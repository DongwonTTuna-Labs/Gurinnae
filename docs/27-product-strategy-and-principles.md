# 27. 제품 전략과 제품 원칙

## 1. 문서 목적

이 문서는 구린네를 기능 목록이 아니라 하나의 제품으로 정의한다. 개발자는 이 문서를 보고 “무엇을 만들 수 있는가”보다 “사용자가 어떤 판단을 더 안전하고 정확하게 내리도록 도와야 하는가”를 먼저 이해해야 한다. 화면, API, 탐지 규칙, 편집 운영은 모두 이 제품 전략에 종속된다.

## 2. 제품 정의

구린네는 대한민국 공공기관의 공개 계약·지출·입찰 자료에서 **조사할 가치가 있는 이상 징후를 발견하고**, 원본·계산·비교 기준·반대 근거·소명·정정 이력을 한곳에서 확인하게 하는 **증거 중심 공공자금 조사 플랫폼**이다.

구린네가 제공하는 핵심 가치는 다음 세 문장으로 고정한다.

1. 시민은 결론만 소비하지 않고 근거와 한계를 직접 확인할 수 있다.
2. 조사자는 대량의 공개자료에서 검토 우선순위를 체계적으로 얻을 수 있다.
3. 조사 대상 기관과 업체는 같은 사건 기록 안에서 소명하고 정정을 요청할 수 있다.

## 3. 해결하려는 문제

현재 공공계약 정보는 여러 기관과 파일 형식에 분산되어 있으며, 동일한 품목·업체·사업을 연결하기 어렵다. 비정상적인 가격이나 반복 계약이 발견되더라도, 비교 조건과 예외 사유를 검증하려면 상당한 시간과 전문성이 필요하다. 반대로 단편적 가격 비교나 선정적 보도는 정상적인 비용 차이를 비리로 오인할 수 있다.

구린네는 다음 문제를 함께 해결해야 한다.

- 발견 문제: 조사해야 할 계약을 대규모 데이터에서 찾기 어렵다.
- 이해 문제: 숫자가 왜 이상한지, 무엇이 아직 확인되지 않았는지 알기 어렵다.
- 검증 문제: 원문과 계산을 재현하기 어렵다.
- 절차 문제: 소명·법률 검토·승인·정정이 분리된 도구에서 이루어진다.
- 신뢰 문제: 사건을 많이 보여주는 것이 정확한 조사보다 우선될 위험이 있다.
- 운영 문제: 데이터 갱신 실패와 모델 비용이 공개 품질에 영향을 줄 수 있다.

## 4. 제품이 하지 않는 일

다음은 범위 밖이며, 제품 지표가 좋아 보이더라도 도입하지 않는다.

- AI가 사람이나 기관의 범죄·부패를 확정하는 기능
- 익명 사용자가 실명 대상을 자유롭게 비난하는 게시판
- 클릭·좋아요·댓글·공유량으로 사건을 순위화하는 기능
- 기관 또는 업체의 “부패 점수”, “구림 순위”, “범죄 확률”
- 유료 고객이 사건의 공개·비공개 또는 조사 우선순위를 변경하는 기능
- 원문과 비교조건 없이 가격 배수만 보여주는 카드
- 조사자가 근거 없이 자유문으로 사실 상태를 변경하는 기능
- 공개된 기록을 흔적 없이 삭제하거나 최신 문장으로 덮어쓰는 기능
- 내부 조사 메모와 민감한 소명자료를 공개 검색에 섞는 기능
- 실제 운영 검증 전의 합성 데이터를 현실 사건처럼 노출하는 기능

## 5. 핵심 사용자 성과

### 5.1 시민과 독자

- 사건의 현재 상태를 30초 안에 이해한다.
- “확인된 사실”, “계산된 결과”, “편집 해석”, “당사자 소명”, “미확인 항목”을 구분한다.
- 원본 문서와 비교 계약을 찾을 수 있다.
- 잘못되거나 오래된 정보를 발견하면 정정 요청을 제출할 수 있다.
- 데이터가 어느 기간과 출처를 포함하는지 알 수 있다.

### 5.2 기자·연구자·시민단체

- 사건과 계약을 안정적인 URL로 인용한다.
- 공개 가능한 데이터와 방법론을 내려받아 재현한다.
- 기관·업체·품목·규칙·기간으로 검색한다.
- 정정·철회·소명 이력을 놓치지 않는다.

### 5.3 내부 조사·편집자

- 신호를 검토하고 오탐을 빠르게 제외한다.
- 하나의 사건에서 가설, 근거, 반대 근거, 주장, 소명, 승인 상태를 관리한다.
- 공개 가능성을 “느낌”이 아니라 명시적인 gate로 확인한다.
- 다른 편집자가 같은 snapshot을 독립적으로 검토할 수 있다.
- 모든 고위험 행동이 감사 로그에 남는다.

### 5.4 기관·업체 소명 담당자

- 요청의 대상, 기한, 공개 예정 범위를 명확히 이해한다.
- 답변과 첨부자료를 임시 저장하고 제출 전에 검토한다.
- 어떤 부분이 공개될 수 있는지 동의 범위를 선택한다.
- 제출 영수증과 이후 처리 상태를 확인한다.

## 6. 제품 원칙

### P-01. 결론보다 증거가 먼저다

사건 상세의 첫 화면은 선정적인 제목보다 상태, 관찰된 사실, 가장 중요한 미확인 항목, 당사자 소명을 우선한다. 모든 핵심 문장은 증거 또는 명시적인 편집 의견에 연결된다.

### P-02. 이상 징후와 위법성을 분리한다

“비교군 중앙값보다 5배 높다”는 계산 결과일 수 있지만, “비리를 저질렀다”는 법적·사실적 판단이다. UI는 둘을 색상과 문구만이 아니라 정보 구조로 분리한다.

### P-03. 불확실성을 숨기지 않는다

누락된 부속 문서, 단위 불명, 유지보수 포함 여부, 데이터 갱신 지연은 작은 각주가 아니라 의사결정에 필요한 1급 정보다.

### P-04. 반대 근거를 같은 무게로 제공한다

조사 가설을 지지하는 자료만 나열하지 않는다. 합리적인 가격 차이, 계약 취소, 사양 차이, 소명자료와 같은 반대 근거를 별도 섹션에 둔다.

### P-05. 정정은 실패가 아니라 제품 기능이다

정정·철회·설명 완료는 숨기지 않고 홈과 사건 상세에서 접근 가능하게 한다. 이전 공개 revision, 변경 이유, 승인자를 보존한다.

### P-06. 공개 읽기는 계정 없이 가능해야 한다

핵심 공공정보를 보기 위해 회원가입을 요구하지 않는다. 알림 구독은 이메일 검증과 관리용 magic link를 사용하며, 읽기 권한과 분리한다.

### P-07. 고위험 행동은 의도와 책임을 확인한다

게시, 철회, 법률 보류, 역할 변경, kill switch는 정확한 대상·영향·이유·최근 재인증·서버 gate를 요구한다. 일반적인 확인창 한 번으로 끝내지 않는다.

### P-08. 탐색은 가능하게, 순위화는 하지 않는다

검색·필터·정렬은 제공하되 기관과 업체를 부패 순위로 만들지 않는다. 통계는 반드시 데이터 범위와 비교 가능 조건을 함께 표시한다.

### P-09. AI는 보조자이고 기록의 주체가 아니다

AI 제안은 결정적 계산과 원문보다 시각적으로 낮은 우선순위를 갖는다. AI는 승인자, 사실 원천, 공개 주체가 될 수 없다.

### P-10. 신뢰 경계를 화면 구조에 반영한다

공개 웹, 내부 콘솔, 소명 포털은 별도 origin·세션·API·CSP·클라이언트를 사용한다. 편의를 이유로 하나의 앱에 합치지 않는다.

## 7. 제품 성공 지표

지표는 “의혹을 많이 생성함”이 아니라 품질과 절차를 측정한다.

### 7.1 공개 이해도

- 사건 상세 방문자의 상태·한계 섹션 도달률
- evidence drawer 또는 원문 열람률
- 방법론·coverage 페이지 도달률
- 사용자 연구에서 상태와 법적 의미를 올바르게 설명한 비율
- 정정된 사건에서 최신 revision을 인지한 비율

### 7.2 조사 품질

- triage 후 실제 사건으로 승격된 signal 비율
- blocker로 조기에 제외된 오탐 비율
- 공개 전 반대 가설 검토 완료율
- claim의 유효 evidence 연결률
- 독립 review에서 반려된 주요 결함 유형
- 공개 후 사실 정정률과 원인 분포

### 7.3 절차 공정성

- 소명 요청 전달 성공률
- 기한 내 응답률
- 응답이 공개 내용에 반영된 비율
- 정정 요청의 최초 검토 시간과 해결 시간
- 법률·편집 gate 우회 시도 0건

### 7.4 운영 신뢰성

- source freshness SLA 충족률
- schema drift 탐지 시간
- 공개 API 가용성
- job DLQ 체류 시간
- 일별 모델 비용 한도 초과 빈도
- public/private data leakage 0건

### 7.5 금지된 허영 지표

다음은 제품 성공의 기준으로 사용하지 않는다.

- 생성된 이상 신호 총량
- 가장 높은 가격 배수
- 기관별 의혹 건수 순위
- 충격적인 제목의 클릭률
- 소셜 공유량
- 사용자의 분노 반응 수


## 8. 최종 제품 범위와 납품 원칙

구린네는 일부 수직 슬라이스, 제한된 공개 웹, 후속 운영 확장으로 나누어 납품하지 않는다.
최종 source tree는 다음을 동시에 포함한다.

- synthetic development mode와 production live connector
- 세 SvelteKit SSR 앱의 94개 화면
- Public, Control, Submission API의 전체 operation
- ingestion, normalization, entity resolution, detection
- signal triage, case investigation, evidence, claim, right of reply
- independent review, publication, correction, retraction
- source, rule, job, provider, budget, audit, access operations
- PostgreSQL migrations, role grants, outbox/inbox/jobs
- Docker development/test/production topology
- CI, backup/restore, observability, security and accessibility tests

구현자는 내부적으로 dependency 순서를 정할 수 있지만, 발주자에게 중간 범위를 최종본으로 제출하지 않는다.
개발용 합성 모드와 운영용 live 모드는 같은 domain/application path를 사용하며 adapter와 설정만 다르다.

## 9. 제품 가설과 검증

각 큰 기능은 구현 전에 검증 가능한 가설을 가져야 한다.

| 가설 | 검증 방식 | 실패 시 대응 |
|---|---|---|
| 사용자가 상태와 위법성을 구분한다 | 5초·30초 이해도 테스트 | 제목·상태·한계 위계 수정 |
| evidence drawer가 신뢰에 도움된다 | 시민·기자 task test | locator와 원문 문맥 개선 |
| 내부 task rail이 조사 누락을 줄인다 | 합성 사건 walkthrough | 작업 그룹과 gate 재설계 |
| response portal이 제출 오류를 줄인다 | 외부 담당자 usability test | 단계·용어·첨부 흐름 단순화 |
| 기관 상세가 순위 없이도 유용하다 | 탐색 task 및 인터뷰 | coverage·비교 맥락 강화 |
| 알림이 선정성을 만들지 않는다 | 구독·해지 사유 분석 | 주제·빈도·문구 제한 |

## 10. 최종 구현 필수 계약

화면 구현은 다음이 모두 충족될 때만 시작한다.

- `specs/ui/screen-catalog.yaml`에 화면이 존재한다.
- 화면의 primary user, job, 질문, 섹션, 행동, 상태가 정의되어 있다.
- 필요한 API operation은 모두 `READY`이며 exact method, path, auth, request/response, errors가 정의되어 있다.
- 권한과 audit 요구사항이 정의되어 있다.
- 공개 문구는 content pattern에 맞는다.
- 모바일과 키보드 경로가 정의되어 있다.
- analytics event가 개인정보 최소화 원칙을 충족한다.
- final design system, screen build manifest와 automated acceptance가 모두 연결되어 있다.

코덱스는 이 조건을 충족하지 않은 화면을 “일반적인 대시보드 관행”으로 추측하여 구현해서는 안 된다.
