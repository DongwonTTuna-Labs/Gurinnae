# UI 절제 계약 — Interface Restraint Contract

status: BINDING (AGENTS.md 수준 강제)
specification_version: 13.0.0+owner-ui-restraint.2
applies_to: 모든 first-party 화면 (public-web 34, response-portal 8, review-console 52)
reference_exemplar: https://hosungseo.github.io/korea100/ (대한민국 제도 지도)
precedence: 이 계약은 시각 언어·카피 톤에 관해 `specs/ui/FINAL_DESIGN_SYSTEM.md`,
  `specs/ui/final-reference/`(정적 프로토타입), `specs/ui/design-tokens.yaml`의
  typography/density 서술과 충돌할 때 우선한다. 데이터·operation·section 구조를 정의하는
  hash-pinned 계약(screen-catalog 등)에는 우선하지 않는다 — §7 참조.

## 0. 왜 이 계약이 존재하는가

구린네의 visual thesis는 "공공 기록 보관소와 탐사 데이터룸"이다 (`design-tokens.yaml` FINAL).
구현 과정에서 UI가 에디토리얼/마케팅 스타일(거대 히어로 타이포, 에세이 문단, 장식 카드)로
드리프트하는 사고가 반복됐다. 이 계약은 그 드리프트를 **구조적으로 불가능**하게 만든다.

구린네는 잡지가 아니라 **장부(ledger)다.** 신뢰는 문장이 아니라 숫자·상태·출처·기준일이 만든다.
구조가 스스로 말하게 하고, UI가 자신을 설명하지 않게 한다.

## 1. 지향 — 레퍼런스에서 가져오는 것

reference_exemplar가 증명한 패턴을 구린네 도메인에 이식한다. 색·폰트 값은 복사하지 않고
(`design-tokens.yaml`의 paper/ink 팔레트가 권위), **구조와 절제**를 복사한다.

| 패턴 | 정의 |
|---|---|
| 대장(ledger) 우선 | 목록 화면의 첫 화면은 밀도 높은 데이터 행이다. 히어로가 아니다 |
| stat 스트립 | 신뢰 지표는 큰 숫자 + 작은 라벨 타일로. 문장으로 풀지 않는다 |
| 기준일 상시 표시 | 데이터 신선도(수집/검증 기준 시각)는 헤더급 1급 정보다 |
| 파셋 + 카운트 | 분류 내비게이션은 항목명 + 건수. 그 자체가 통계다 |
| 상태 = 점 + 라벨 | 상태는 색점과 2~4어 라벨. 배지 남발·문장 설명 금지 |
| 커버리지 정직성 | 확인 N건 / 미확인 M건처럼 검증 범위를 숫자로 상시 노출 |
| 정정 로그 인라인 | revision·정정·미검증 표시를 숨기지 않고 본문 흐름에 한 줄로 |
| 미확인의 1급 시민화 | "확인 못 한 것"이 별도 대장으로 전면에 선다 |
| 비교 선반 | 항목 선택 → 하단 선반 → 같은 기준 표로 나란히 |
| 백과사전 내비게이션 | 상세 화면은 이전/다음 + 위치(N/전체) 순차 탐색 제공 |

## 2. 금지 목록 (hard — 위반은 완료 불가)

1. **히어로 타이포그래피**: 데스크톱 뷰포트에서 렌더된 제목 글자 크기 40px 초과 금지.
   화면 제목의 표준은 24~32px다.
2. **마케팅·에세이 문단**: 제품 가치를 서술하는 산문("~를 찾고, ~를 보여줍니다",
   "결론보다 상태와 근거를 먼저 봅니다" 류) 금지. 가치는 데이터가 증명한다.
3. **자기설명 UI**: 화면이 자기 구조를 문장으로 설명하지 않는다
   ("확인·미확인·소명을 분리해서 봅니다" 금지 — 분리된 레이아웃 자체가 그 말을 한다).
4. **페이지 인트로 문단**: 제목 아래 설명 문단 금지. 필요하면 부제 **한 줄**(1문장)까지.
5. **장식 요소**: 그라데이션, 일러스트, 아이콘 남발, 그림자 카드 스택, 배경 패턴,
   스크롤 연출 애니메이션 금지 (`design-tokens.yaml` forbidden_styles의 확장).
6. **카드 부풀리기**: 체크박스 하나·필드 하나를 카드로 감싸 공간을 늘리는 패턴 금지.
   파셋·필터는 컴팩트 리스트/칩으로.
7. **부차 CTA**: 화면당 primary CTA는 최대 1개. "업데이트 구독" 같은 부차 유도는
   푸터 텍스트 링크로 강등.
8. **감탄·과장 어휘**: "혁신", "간편하게", "만나보세요", "쉽고 빠르게", 이모지, 느낌표 금지.
9. **빈 공간 연출**: 목록·대장 화면(1440×900)에서 첫 화면에 데이터 행 8개 미만이면 실패.
   여백은 정보 밀도를 이기지 못한다.
10. **중복 안내문**: 같은 안전 문구·안내문을 화면마다 문단으로 반복 금지. §4의 압축 규칙을 따른다.

## 3. 필수 구성 (화면 유형별)

### 3.1 대장(목록) 화면 — 사례·계약·기관·업체·source 목록
- 컴팩트 헤더(로고 + 내비 링크 + 기준일) → 검색/stat 스트립 → 파셋 사이드바 + 데이터 테이블
- 테이블 행: 식별자 / 제목 + 한 줄 요약 / 유형 / 분류 칩 / 상태 점+라벨 / 핵심 수치
- 정렬 토글은 텍스트 버튼 2~3개, 드롭다운 남발 금지
- 모바일: 파셋은 가로 스크롤 칩, 행은 제목 + 요약 + 메타 한 줄로 붕괴. DOM 순서 유지

### 3.2 상세 화면 — 사례·계약·기관 상세
- 상단: 목록 복귀 + 이전/다음 + 위치(N/전체)
- 제목 위 메타 라인: 번호 + 분류 칩 + 상태 + 커버리지(확인 n·미확인 m·소명 k) + revision
- 제목 직하: 대상별 stat 타일(관측 계약 수, 비교군 크기, 데이터 범위, 최근 수집 등)
- 본문: "한 장" 원칙 — 확인 사실 / 중요한 미확인 / 소명 / 돈·문서의 흐름 / 데이터 범위 /
  관련 항목을 스크롤 한 번의 섹션 그리드로. 섹션 제목은 명사구 2~4어
- 하단: 정정·갱신 로그 (날짜 + 무엇이 + 근거, 한 줄 단위)

### 3.3 폼 화면 — 소명 제출, 정정 요청, 제보
- 필드 + 한 줄 도움말. 프라이버시·저장 정책은 **정직한 한 줄**로 명시
- primary CTA 1개. 성공/실패는 문장 대신 상태 + 다음 행동으로

### 3.4 내부 콘솔 (review-console)
- 이미 기능 밀도가 있으므로 유지하되 §2 금지 목록 동일 적용
- 대시보드 서사 문구("다음으로 무엇을 확인해야 하는가" 류 수사적 제목) → 명사구 라벨로

## 4. 카피 규칙 (copy-guidelines.md의 절제 확장)

- 라벨은 명사구. 문장형 라벨 금지 ("검토 기준" O, "우리는 이렇게 검토합니다" X)
- 법적 안전 문구(예: 자동 부패 판정 아님, 위법성 미확정)는 **삭제 불가**이며 압축 시
  의미 축소 금지 (면책 대상·조건을 빠뜨리는 압축은 위반). 단:
  - 전 화면 공통 문구는 헤더/푸터의 지정 슬롯 **한 줄**로 1회
  - 상태 의존 문구는 **상시 보조 텍스트**로 압축한다. 툴팁·hover 의존 금지 —
    모바일·터치에서 비노출된다
  - `copy-guidelines.md`의 상태별 표준 문구는 해당 상태 최초 노출 지점에서만 전문 표기
  - attestation·동의 범위·제출 영수증 고지·개인정보 보호 고지는 압축 자체 금지 (위치 이동만)
- 수치·상태·출처·시점은 항상 라벨+값 쌍. 문장에 녹이지 않는다
- 도메인 어휘 통일: 목록 화면은 "~ 대장"으로 명명한다 (사례 대장, 계약 대장, 미확인 대장)

## 5. 측정 가능한 게이트 (리뷰어·구현자 공용)

데스크톱 1440×900 기준, 각 화면에서:

| # | 게이트 | 기준 |
|---|---|---|
| G1 | 최대 제목 크기 | 렌더된 font-size ≤ 40px (표준 24~32px) |
| G2 | 서술 문단 수 | 2문장 이상 `<p>` ≤ 1개/화면 (법적 전문 표기 지점 제외) |
| G3 | 대장 첫 화면 밀도 | 데이터 행 ≥ 8 |
| G4 | primary CTA | ≤ 1개/화면 |
| G5 | 기준일/신선도 | 공개 화면 전부에 수집·검증 기준 시각 노출 |
| G6 | 커버리지 수치 | 사례·계약 상세에 확인/미확인/소명 카운트 노출 |
| G7 | 자기설명 문구 | "~를 보여줍니다/봅니다/제공합니다" 패턴 0건 |
| G8 | 스크린샷 증거 | 변경 화면 전부 실제 렌더 스크린샷 확보 (코드 리뷰만으로 통과 금지) |
| G9 | 최소 글자 크기 | 렌더된 본문·메타 텍스트 ≥ 12px (밀도는 여백·행높이로 얻는다, 글자 축소로 얻지 않는다) |
| G10 | 스크롤 예산 | 실뷰포트 1440×900에서 `document.scrollHeight / 900` — 데이터 있는 상세·대장 화면 ≤ 1.8배, 폼·워크스페이스 ≤ 2.2배. 첫 화면(위 900px)에 그 화면의 핵심 정보 단위(대장=데이터 행, 상세=확인/미확인/소명 또는 stat)가 반드시 들어온다 |

**G10이 핵심이다.** korea100은 "한 장(one canvas)"이다 — 정보를 세로로 나열하지 않고
가로로 압축한다. 라벨+값은 세로 스택이 아니라 stat 타일·다열 표로 붙인다. 섹션 헤더·상태
반복·빈 상태 안내로 세로 부피를 낭비하지 않는다. **fullPage 스크린샷으로 "밀도 좋다"고
판정하지 않는다 — 반드시 실뷰포트 above-the-fold + scrollHeight 배수로 측정한다.**

G5·G6는 해당 데이터가 화면의 projection/contract에 존재하는 범위에서 판정한다.
데이터가 계약상 없으면 N/A로 보고하고 계약 개정 라운드로 이월한다.
G10은 리뷰어가 실뷰포트 스크린샷과 scrollHeight를 직접 측정해 판정한다 (자기 보고 불가).

## 6. 구현자(codex) 특별 조항

- 이 계약과 다른 스펙이 충돌하면 임의 해석하지 말고 `implementation-evidence/spec-conflicts.md`에
  기록하고 fail-closed로 멈춘다.
- 시각 검증을 스냅샷 갱신으로 우회하지 않는다. 스냅샷 갱신은 이 계약 준수를 증명하는
  스크린샷 evidence와 함께만 허용된다.
- "텍스트만 줄이고 구조는 유지"는 준수가 아니다. §3의 구성 자체를 구현해야 한다.
- 새 화면·컴포넌트를 만들 때 이 계약의 §2·§3을 먼저 읽고, 완료 보고에 §5 게이트별
  자체 점검 결과를 포함한다.

## 7. 단계적 적용 (staged application)

이 계약의 §1/§3 구성 중 일부(이전/다음 내비게이션, 비교 선반, 전역 신선도 슬롯,
"~대장" 화면 명명 등)는 hash-pinned v13 계약(screen catalog, operation 계약)의 개정
없이는 구현할 수 없다. 이 경우:

- **밀도·타이포·카피·장식 규칙(§2, §4, §5)은 즉시 적용한다** — 데이터가 필요 없다.
- 계약 개정이 필요한 구성 항목은 `implementation-evidence/spec-conflicts.md`에 기록하고
  계약 개정 라운드로 이월한다. 이 기록·이월은 §6의 fail-closed 중단 사유가 아니다.
- 어떤 경우에도 **데이터를 발명해 구성 요건을 채우지 않는다** — 신선도·커버리지 수치가
  없으면 그 UI 요소를 만들지 않는 것이 정답이다.
