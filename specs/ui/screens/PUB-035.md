# PUB-035 — 후원

- 상태: **FINAL / REQUIRED COMPLETE**
- Route: `/donate`
- Surface: `public`
- Access: `anonymous`
- Archetype: `GUIDED_FORM`
- Test prefix: `pub_035`

## 사용자 목적

후원 기능의 운영 가능 상태와 독립성 원칙을 확인하고, 허용된 환경에서만 후원 의향을 접수한다.

## 이 화면이 즉시 답해야 하는 질문

- 현재 후원 기능을 사용할 수 있는가?
- 어떤 주기와 결제 공급자가 허용되는가?
- 접수 결과가 결제 성공을 의미하는가?

## Above-the-fold 순서

1. `mode`
2. `independence`
3. `donation`
4. `receipt`

1440×900 wide viewport에서 사용자는 스크롤 전에 운영 가능 상태, 독립성 고지, 사용 가능한 입력과 접수 상태를 확인해야 한다. 마케팅 문단이나 장식 카드로 이 상태를 밀어내지 않는다.

## 최종 정보 순서

| 순서 | Section ID | 제목 | 구현 Component | 목적 |
|---:|---|---|---|---|
| 1 | `mode` | 운영 상태 | `StatusAndRevisionHeader` | 테스트 전용 제안만 제공하며 운영 기준이 없으면 후원을 접수하지 않습니다. |
| 2 | `independence` | 후원 독립성 | `KnownUnknownResponse` | `후원은 접근권이 아니며 조사 대상 면제가 아닙니다`를 정확히 표시한다. |
| 3 | `donation` | 후원 의향 | `GuidedFormSection` | 테스트 전용 금액대와 일회·정기 후원, 결제사 선택을 확인합니다. |
| 4 | `receipt` | 접수 상태 | `DecisionReceipt` | 접수 대기 영수증만 표시하며 결제·청구 성공을 뜻하지 않습니다. |

이 순서는 wide, medium, compact에서 의미적으로 동일하다. 화면 폭은 배치를 바꾸지만 중요도를 바꾸지 않는다.

## Layout

- Wide: 12-column; status and independence 12; donation form 8 + receipt/status rail 4
- Medium: 8-column; status and independence precede form and receipt
- Compact: single column preserving `mode → independence → donation → receipt`
- Container: `public_main`

## Actions

| Action ID | Label | Interaction | Assurance | Capability | Operation |
|---|---|---|---|---|---|
| `queue-donation` | 후원 의향 접수 | `COMMAND` | `NONE` | `none` | `private.QueueDonationIntent` |
| `contact` | 문의 | `NAVIGATION` | `NONE` | `none` | `local-only` → `PUB-026 /contact` |

Primary action: `queue-donation`

- Production에서는 `queue-donation`을 비활성화하고 `UNAVAILABLE`을 표시한다.
- `TEST_ONLY`에서만 ephemeral `TEST_FIXTURE` offer를 사용할 수 있다.
- Cadence는 정확히 `ONE_TIME | RECURRING`이다.
- Provider는 정확히 `TOSS_PAYMENTS | KAKAO_PAY | STRIPE`다.
- `PUB-026`에 후원 전용 문의 category를 추가하지 않는다.

## Data contracts

| Operation | API | Method | Path | Request Schema | Response Schema | Success |
|---|---|---|---|---|---|---:|
| `private.GetDonationFixtureOffer` | `billing-gateway-private` | `GET` | `/internal/v1/donation-offers` | `GetDonationFixtureOfferRequestV1` | `DonationFixtureOfferV1` | `200` |
| `private.QueueDonationIntent` | `billing-gateway-private` | `POST` | `/internal/v1/donation-intents` | `DonationIntentQueueRequestV1` | `DonationIntentQueuedReceiptV1` | `202` |

두 operation은 public-web SvelteKit server load/action만 호출한다. 브라우저는 billing-gateway private endpoint, service assertion 또는 `paymentAuthorizationToken`을 직접 받거나 호출하지 않는다.

`DonationFixtureOfferV1`은 다음 공개 가능 필드만 화면별 view-model로 투영한다.

- `schemaVersion`
- `authority`
- `offerVersionId`
- `offerDigest`
- `currency`
- `tiers[]`의 `tierId`, `amountWholeKrw`
- `cadences`
- `providers`
- `productionReadinessEffect`

Production의 service 상태는 `DISABLED`, UI 상태는 `UNAVAILABLE`이다. 503 응답에서 tier, 금액 또는 provider 준비 상태를 발명하지 않는다.

## Receipt contract

- 성공 HTTP status는 `202`다.
- 화면이 표시할 접수 상태는 정확히 `QUEUED`다.
- `QUEUED`는 payment success 또는 charge success를 증명하지 않는다.
- Receipt에는 raw service assertion, payment authorization token, provider credential 또는 재사용 가능한 결제 자료가 포함되지 않는다.

## Required states

- `loading`
- `success`
- `empty`
- `partial`
- `stale`
- `error`
- `method-unavailable`
- `receipt`

상태가 달라도 `mode → independence → donation → receipt` 정보 위계를 유지한다. Production `UNAVAILABLE`은 빈 성공 화면이나 임의의 fixture tier로 대체하지 않는다.

## Responsive contract

- Compact에서 운영 불가 상태, 독립성 고지와 주요 action을 숨기지 않는다.
- 입력 control과 error summary는 DOM 순서와 keyboard 순서를 유지한다.
- Receipt rail은 compact에서 form 뒤의 inline section으로 이동한다.
- Horizontal scrolling만으로 핵심 작업을 해결하지 않는다.

## Accessibility contract

- H1은 정확히 하나다.
- Section heading level을 건너뛰지 않는다.
- Keyboard만으로 허용된 TEST_ONLY task를 완료할 수 있다.
- 최소 pointer target은 44×44 CSS px다.
- `UNAVAILABLE`, validation error와 `QUEUED` 상태는 색상에만 의존하지 않는다.
- Error summary는 해당 입력과 연결되고 실패 후 입력을 보존한다.
- 접수 결과는 live region으로 한 번 알리고 focus를 receipt heading으로 이동한다.

## Analytics allowlist

허용된 analytics event가 없다. 후원 선택, tier, provider, token, assertion, receipt identity 또는 결제 관련 값은 analytics payload에 포함하지 않는다.

## Acceptance

- Route와 access mode가 일치한다.
- Section 순서를 바꾸지 않는다.
- Production은 `UNAVAILABLE`이고 action은 disabled다.
- `TEST_ONLY`는 ephemeral `TEST_FIXTURE` offer만 사용한다.
- Private billing operations는 server-only wrapper에서만 호출한다.
- `QUEUED`를 결제·청구 성공으로 표현하지 않는다.
- 후원은 entitlement나 계약을 생성하지 않으며 공개 접근성을 변경하지 않는다.
- Production/live payment credential은 존재하지 않으며 `TEST_ONLY` fixture는 이를 포함하거나 요구하지 않는다.
- 정확한 독립성 고지를 모든 상태에서 유지한다.
- Compact에서 정보와 행동이 소실되지 않는다.
