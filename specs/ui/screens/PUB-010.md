# PUB-010 — 업체 상세

상태: **FINAL / REQUIRED COMPLETE**  
Route: `/suppliers/{supplierSlug}`  
Surface: `public`  
Access: `anonymous`  
Archetype: `ENTITY_DETAIL`  
Test prefix: `pub_010`

## 사용자 목적

업체 identity와 공공계약 맥락, 공개 사건, 설명·정정을 확인한다.

## 이 화면이 즉시 답해야 하는 질문

- 이 업체가 어떤 공공계약을 체결했는가?
- 같은 이름의 다른 업체와 구분됐는가?
- 관련 공개 기록은 어떤 상태인가?

## Above-the-fold 순서

1. `identity`
2. `coverage`
3. `metrics`
4. `contracts`

1440×900 wide viewport에서 사용자는 스크롤 전에 화면 목적, 객체 상태, 가장 중요한 답, 주요 행동, freshness 또는 blocker를 확인해야 한다.

## 최종 정보 순서

| 순서 | Section ID | 제목 | 구현 Component | 목적 |
|---:|---|---|---|---|
| 1 | `identity` | 업체 식별 정보 | `KnownUnknownResponse` | 공식명·식별·변경 이력·확인 한계. |
| 2 | `coverage` | 수집 범위 | `CoverageStatement` | source·기간. |
| 3 | `metrics` | 계약 현황 통계 | `ComparisonWorkbench` | 계약·기관 분포와 denominator. |
| 4 | `contracts` | 계약 | `StructuredContentSection` | 관측된 계약. |
| 5 | `cases` | 공개 사건 | `StatusAndRevisionHeader` | 상태별. |
| 6 | `corrections` | 설명·정정 | `RevisionAndCorrectionPanel` | identity 수정 포함. |
| 7 | `relationships` | 확인된 관계 | `KnownUnknownResponse` | 공식 자료로 확인된 관계만. |

이 순서는 wide, medium, compact에서 의미적으로 동일하다. 화면 폭은 배치를 바꾸지만 중요도를 바꾸지 않는다.

## Data contracts

| Operation | API | Method | Path | Request Schema | Response Schema |
|---|---|---|---|---|---|
| `getSupplier` | `public-api` | `GET` | `/v1/suppliers/{supplierId}` | `getSupplierQuery` | `SupplierResponse` |
| `listSupplierContracts` | `public-api` | `GET` | `/v1/suppliers/{supplierId}/contracts` | `listSupplierContractsQuery` | `SupplierContractsPage` |
| `listSupplierCases` | `public-api` | `GET` | `/v1/suppliers/{supplierId}/cases` | `listSupplierCasesQuery` | `SupplierCasesPage` |
| `createSubscription` | `submission-api` | `POST` | `/v1/subscription-session` | `createSubscriptionRequest` | `createSubscriptionReceipt` |

모든 Submission operation은 raw bearer token을 canonical URL에 남기지 않는다. Magic token은 BFF가 one-time exchange에만 사용하고 이후에는 scoped submission session으로 전환한다.

## Required states

- `loading`
- `success`
- `empty`
- `partial`
- `stale`
- `error`

상태가 달라도 동일한 정보 위계를 유지한다. Skeleton은 실제 content shape와 일치해야 하며 가짜 성공 값은 표시하지 않는다.

## Responsive contract

- Compact에서 주요 action과 critical unknown/blocker를 숨기지 않는다.
- Primary table은 의미가 보존되는 record list로 재배치한다.
- Context panel은 drawer 또는 inline section으로 이동하며 focus가 복원된다.
- Horizontal scrolling만으로 핵심 작업을 해결하지 않는다.

## Accessibility contract

- H1은 정확히 하나다.
- Section heading level을 건너뛰지 않는다.
- Keyboard만으로 전체 task를 완료할 수 있다.
- 최소 pointer target은 44×44 CSS px다.
- 상태는 색상에만 의존하지 않는다.
- Dialog/drawer 종료 후 원래 trigger로 focus를 되돌린다.
- Chart가 있으면 같은 사실을 담은 표 또는 문장형 대안을 제공한다.
- Save/submit/session exchange 결과를 적절한 live region으로 알린다.

## Analytics allowlist

- `public.supplier.viewed`
- `public.supplier.contract_opened`
- `public.subscription.started`

본문·magic token·scoped session·개인정보·첨부파일명·근거 원문은 analytics payload에 포함하지 않는다.

## Acceptance

- Route와 access mode가 일치한다.
- Section 순서를 바꾸지 않는다.
- 모든 blocking operation을 generated client의 server-only wrapper로 호출한다.
- 모든 필수 상태를 실제 계약으로 구현한다.
- Compact에서 정보와 행동이 소실되지 않는다.
- 권한과 scoped session은 server가 다시 검사한다.
- Screen-specific 금지사항과 global editorial/security policy를 위반하지 않는다.
