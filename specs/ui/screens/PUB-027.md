# PUB-027 — 정정 요청

상태: **FINAL / REQUIRED COMPLETE**  
Route: `/correction-request`  
Surface: `public`  
Access: `anonymous`  
Archetype: `GUIDED_FORM`  
Test prefix: `pub_027`

## 사용자 목적

정확한 공개 claim/revision을 지정해 오류와 근거를 제출한다.

## 이 화면이 즉시 답해야 하는 질문

- 무엇이 잘못됐는가?
- 어느 문장·revision인가?
- 어떤 근거가 있는가?

## Above-the-fold 순서

1. `intro`
2. `target`
3. `issue`
4. `evidence`

1440×900 wide viewport에서 사용자는 스크롤 전에 화면 목적, 객체 상태, 가장 중요한 답, 주요 행동, freshness 또는 blocker를 확인해야 한다.

## 최종 정보 순서

| 순서 | Section ID | 제목 | 구현 Component | 목적 |
|---:|---|---|---|---|
| 1 | `intro` | 절차·긴급 안내 | `StatusAndRevisionHeader` | 정정 요청 절차와 긴급 사안 경로. |
| 2 | `target` | 대상 선택 | `StatusAndRevisionHeader` | URL·revision·claim. |
| 3 | `issue` | 오류 설명 | `GuidedFormSection` | 유형·설명·제안 수정. |
| 4 | `evidence` | 근거 | `EvidenceLedger` | 링크·파일. |
| 5 | `privacy` | 연락·공개 동의 | `StructuredContentSection` | 최소화. |
| 6 | `review` | 검토 | `DecisionReviewPanel` | check answers. |

이 순서는 wide, medium, compact에서 의미적으로 동일하다. 화면 폭은 배치를 바꾸지만 중요도를 바꾸지 않는다.

## Layout

- Wide: 12-column; form centered in columns 3–10; summary rail columns 10–12 only on review step
- Medium: 8-column centered
- Compact: single column; sticky save/continue bar does not cover fields
- Container: `response`

## Data contracts

| Operation | API | Method | Path | Request Schema | Response Schema |
|---|---|---|---|---|---|
| `createCorrectionRequestDraft` | `submission-api` | `POST` | `/v1/correction-session` | `createCorrectionRequestDraftRequest` | `createCorrectionRequestDraftReceipt` |
| `getCorrectionRequestDraft` | `submission-api` | `GET` | `/v1/correction-session` | `getCorrectionRequestDraftQuery` | `CorrectionRequestDraft` |
| `saveCorrectionRequestDraft` | `submission-api` | `PUT` | `/v1/correction-session` | `saveCorrectionRequestDraftRequest` | `saveCorrectionRequestDraftReceipt` |
| `createCorrectionAttachment` | `submission-api` | `POST` | `/v1/correction-session/attachments` | `createCorrectionAttachmentRequest` | `createCorrectionAttachmentReceipt` |
| `finalizeCorrectionAttachment` | `submission-api` | `POST` | `/v1/correction-session/attachments/{attachmentId}:finalize` | `finalizeCorrectionAttachmentRequest` | `finalizeCorrectionAttachmentReceipt` |
| `deleteCorrectionAttachment` | `submission-api` | `DELETE` | `/v1/correction-session/attachments/{attachmentId}` | `deleteCorrectionAttachmentRequest` | `deleteCorrectionAttachmentReceipt` |
| `getCorrectionRequestDraftPreview` | `submission-api` | `GET` | `/v1/correction-session/preview` | `getCorrectionRequestDraftPreviewQuery` | `CorrectionDraftPreviewResponse` |
| `createCorrectionRequest` | `submission-api` | `POST` | `/v1/correction-session:submit` | `createCorrectionRequestRequest` | `createCorrectionRequestReceipt` |

모든 Submission operation은 raw bearer token을 canonical URL에 남기지 않는다. Magic token은 BFF가 one-time exchange에만 사용하고 이후에는 scoped submission session으로 전환한다.

## Required states

- `loading`
- `success`
- `empty`
- `partial`
- `stale`
- `error`

상태가 달라도 동일한 정보 위계를 유지한다. Skeleton은 실제 content shape와 일치해야 하며 가짜 성공 값은 표시하지 않는다.

## Responsive contract

- Compact에서 주요 action과 critical unknown/blocker를 숨기지 않는다.
- Primary table은 의미가 보존되는 record list로 재배치한다.
- Context panel은 drawer 또는 inline section으로 이동하며 focus가 복원된다.
- Horizontal scrolling만으로 핵심 작업을 해결하지 않는다.

## Accessibility contract

- H1은 정확히 하나다.
- Section heading level을 건너뛰지 않는다.
- Keyboard만으로 전체 task를 완료할 수 있다.
- 최소 pointer target은 44×44 CSS px다.
- 상태는 색상에만 의존하지 않는다.
- Dialog/drawer 종료 후 원래 trigger로 focus를 되돌린다.
- Chart가 있으면 같은 사실을 담은 표 또는 문장형 대안을 제공한다.
- Save/submit/session exchange 결과를 적절한 live region으로 알린다.

## Acceptance

- Route와 access mode가 일치한다.
- Section 순서를 바꾸지 않는다.
- 모든 blocking operation을 generated client의 server-only wrapper로 호출한다.
- 모든 필수 상태를 실제 계약으로 구현한다.
- Compact에서 정보와 행동이 소실되지 않는다.
- 권한과 scoped session은 server가 다시 검사한다.
- Screen-specific 금지사항과 global editorial/security policy를 위반하지 않는다.
