# PUB-004 — 사건 상세

상태: **FINAL / REQUIRED COMPLETE**  
Route: `/cases/{caseSlug}`  
Surface: `public`  
Access: `anonymous`  
Archetype: `EVIDENCE_LANDING`  
Test prefix: `pub_004`

## 사용자 목적

사건의 현재 상태·확인 사실·중요한 미확인·당사자 소명·근거를 책임 있게 이해한다.

## 이 화면이 즉시 답해야 하는 질문

- 현재 무엇이 확인됐는가?
- 무엇이 아직 확인되지 않았는가?
- 당사자는 무엇이라고 답했는가?
- 원문과 계산을 검증할 수 있는가?

## Above-the-fold 순서

1. `status`
2. `known`
3. `unknown`
4. `response`

1440×900 wide viewport에서 사용자는 스크롤 전에 화면 목적, 객체 상태, 가장 중요한 답, 주요 행동, freshness 또는 blocker를 확인해야 한다.

## 최종 정보 순서

| 순서 | Section ID | 제목 | 구현 Component | 목적 |
|---:|---|---|---|---|
| 1 | `status` | 상태·개정·최신성 | `StatusAndRevisionHeader` | 최신 공개 상태·정정·개정 기준. |
| 2 | `known` | 확인된 사실 | `KnownUnknownResponse` | source에 연결된 사실과 계산. |
| 3 | `unknown` | 중요한 미확인 | `KnownUnknownResponse` | 판단을 바꿀 수 있는 누락 정보. |
| 4 | `response` | 기관·업체 소명 | `StatusAndRevisionHeader` | 응답 상태·제출일·검증 범위. |
| 5 | `comparison` | 비교 맥락 | `ComparisonWorkbench` | cohort·제외·분포·단위. |
| 6 | `counter` | 반대 근거 | `EvidenceLedger` | 대안 설명과 반박 자료. |
| 7 | `evidence` | 근거·원문 | `EvidenceLedger` | claim별 locator와 provenance. |
| 8 | `timeline` | 조사·공개 이력 | `RevisionTimeline` | 공개 가능한 사건 timeline. |
| 9 | `revision` | 정정·개정 이력 | `StatusAndRevisionHeader` | 불변 revision과 변경 이유. |

이 순서는 wide, medium, compact에서 의미적으로 동일하다. 화면 폭은 배치를 바꾸지만 중요도를 바꾸지 않는다.

## Layout

- Wide: 12-column public grid; status/title 12; known-unknown-response 12; main evidence 8 + sticky context 4
- Medium: 8-column grid; all primary regions span 8; context follows comparison
- Compact: single column preserving status → known → unknown → response → comparison → evidence → history
- Container: `public_main`

## Data contracts

| Operation | API | Method | Path | Request Schema | Response Schema |
|---|---|---|---|---|---|
| `getPublicCase` | `public-api` | `GET` | `/v1/cases/{caseSlug}` | `getPublicCaseQuery` | `PublicCaseResponse` |
| `listCaseRevisions` | `public-api` | `GET` | `/v1/cases/{caseSlug}/revisions` | `listCaseRevisionsQuery` | `CaseRevisionsPage` |
| `getCaseReproducibility` | `public-api` | `GET` | `/v1/cases/{caseSlug}/reproducibility` | `getCaseReproducibilityQuery` | `CaseReproducibilityResponse` |

모든 Submission operation은 raw bearer token을 canonical URL에 남기지 않는다. Magic token은 BFF가 one-time exchange에만 사용하고 이후에는 scoped submission session으로 전환한다.

## Required states

- `loading`
- `success`
- `empty`
- `partial`
- `stale`
- `error`

상태가 달라도 동일한 정보 위계를 유지한다. Skeleton은 실제 content shape와 일치해야 하며 가짜 성공 값은 표시하지 않는다.

## Responsive contract

- Compact에서 주요 action과 critical unknown/blocker를 숨기지 않는다.
- Primary table은 의미가 보존되는 record list로 재배치한다.
- Context panel은 drawer 또는 inline section으로 이동하며 focus가 복원된다.
- Horizontal scrolling만으로 핵심 작업을 해결하지 않는다.

## Accessibility contract

- H1은 정확히 하나다.
- Section heading level을 건너뛰지 않는다.
- Keyboard만으로 전체 task를 완료할 수 있다.
- 최소 pointer target은 44×44 CSS px다.
- 상태는 색상에만 의존하지 않는다.
- Dialog/drawer 종료 후 원래 trigger로 focus를 되돌린다.
- Chart가 있으면 같은 사실을 담은 표 또는 문장형 대안을 제공한다.
- Save/submit/session exchange 결과를 적절한 live region으로 알린다.

## Acceptance

- Route와 access mode가 일치한다.
- Section 순서를 바꾸지 않는다.
- 모든 blocking operation을 generated client의 server-only wrapper로 호출한다.
- 모든 필수 상태를 실제 계약으로 구현한다.
- Compact에서 정보와 행동이 소실되지 않는다.
- 권한과 scoped session은 server가 다시 검사한다.
- Screen-specific 금지사항과 global editorial/security policy를 위반하지 않는다.
