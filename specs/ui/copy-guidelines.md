# 구린네 UI·편집 문구 지침

## 1. 목적

문구는 제품의 법적·윤리적 안전장치다. 데이터 이상을 사람의 범죄나 도덕성으로 바꾸어 표현하지 않는다. 문장은 근거 수준, 계산 결과, 미확인 사항, 소명 상태를 정확히 구분해야 한다.

## 2. 기본 문체

- 사실 중심의 평서문
- 주어와 출처 명시
- 계산 기준과 기간 명시
- 불확실성을 숨기지 않음
- 자극적인 수사, 조롱, 은어 금지
- 기관·업체·개인을 동일 기준으로 존중
- “확인했다”, “계산됐다”, “자료에 따르면”의 주체를 구분

서비스명은 구린네지만 본문은 “구리다”라는 감정적 판정을 반복하지 않는다.

## 3. 용어 사전

| 내부 개념 | 공개 권장 표현 | 금지/주의 표현 |
|---|---|---|
| anomaly signal | 이상 징후, 비교 필요 신호 | 비리 적발, 범죄 탐지 |
| internal priority | 공개하지 않음 | 부패 확률, 구림 점수 |
| investigation | 자료 검토, 추가 조사 | 수사(공식 수사기관이 아닌 경우) |
| subject | 관련 기관/업체/계약 | 피의자, 범인 |
| no response | 기한 내 답변을 받지 못했습니다 | 해명하지 못했습니다, 인정했습니다 |
| explained | 가격 차이에 대한 설명이 확인됐습니다 | 무혐의(공식 처분 아님) |
| officially confirmed | 공식 감사/처분/판결에서 확인 | 유죄(판결 맥락 없이) |
| retracted | 게시를 철회했습니다 | 삭제해 드렸습니다 |
| model output | AI 보조 분석 | AI 판결, AI 감사 결과 확정 |

## 4. 상태별 표준 문구

### `PUBLISHED_ANOMALY`

> 공개자료 비교에서 설명이 필요한 차이가 확인됐습니다. 현재 자료만으로 위법성이나 부패 여부를 판단할 수 없습니다.

### `PUBLISHED_EXPLAINED`

> 처음 탐지된 차이는 추가 자료에서 확인된 구성·서비스·조건의 차이로 설명됩니다. 탐지와 검증 과정을 함께 공개합니다.

### `OFFICIALLY_CONFIRMED`

> [공식 기관/법원]의 [문서 종류·날짜]에서 [정확한 확인 범위]가 확인됐습니다. 구린네의 자체 판단이 아니라 해당 공식 결과를 요약합니다.

### `CORRECTED`

> 이 페이지는 [날짜]에 정정됐습니다. [무엇이 잘못됐는지]와 [결론에 미친 영향]을 아래 정정 기록에서 확인할 수 있습니다.

### `RETRACTED`

> 핵심 근거의 오류로 이 게시물을 철회했습니다. 원래 주장은 더 이상 유효하지 않습니다. 오류 원인과 후속 조치를 공개합니다.

### `TEMPORARILY_RESTRICTED`

> 법적 사유, 권리 보호 또는 안전을 위해 공개를 일시 제한했습니다. 이 제한은 위법성이나 부패 여부에 대한 판단이 아닙니다.

## 5. 가격 비교 문장 템플릿

좋은 예:

> 2025년 1월부터 12월까지 같은 분류·단위·부가세 기준을 충족한 공공계약 12건의 단가 중앙값은 480,000원이었습니다. 이 계약의 공개 단가는 2,400,000원으로 5.0배였습니다.

> 다만 유지보수와 인증 비용이 단가에 포함됐는지는 공개자료에서 확인되지 않아, 해당 비교만으로 부당한 가격이라고 결론 내릴 수 없습니다.

나쁜 예:

> 인터넷 최저가보다 5배나 비싸게 해먹었다.

> AI가 세금 낭비 가능성을 93%로 판단했다.

## 6. 관계·집중도 문장 템플릿

좋은 예:

> 분석 가능한 동일 범주의 계약금액 중 64%가 한 업체와 체결됐습니다. 시장 구조, 프레임워크 계약, 독점권 여부는 별도 확인이 필요합니다.

나쁜 예:

> 이 기관은 특정 업체와 유착한 것으로 보입니다.

동일 주소·전화번호 등 shared identifier는 공개 전에 법적 관련성, 데이터 공개 적법성, 같은 건물/대행사/회계사 등 대안 설명을 반드시 검토한다.

## 7. 소명 문구

- 당사자의 말을 구린네의 사실 판단처럼 섞지 않는다.
- 직접 인용은 필요한 범위만 사용한다.
- 요약은 의미를 바꾸지 않고 검토 가능하게 원문을 보존한다.
- 답변이 없으면 중립적으로 표시한다.

예:

> 가상새빛시청은 2026년 1월 25일 “계약금액에 3년 유지보수와 현장 교육이 포함됐다”고 답했습니다. 구린네는 제출된 산출내역서에서 해당 항목을 확인했고, 비교 가능 단가를 다시 계산했습니다.

## 8. 불확실성 표현

권장:

- 공개자료에서는 확인되지 않았습니다.
- 자료 간 값이 일치하지 않습니다.
- 동일 제품인지 확인할 수 없습니다.
- 표본 수가 적어 일반화하기 어렵습니다.
- 다음 조건이 달라 직접 비교하지 않았습니다.
- 기관/업체 식별이 모호해 공개 대상에서 제외했습니다.

회피할 표현:

- 아마도
- 틀림없이
- 상식적으로
- 누가 봐도
- 정황상 확실

## 9. 숫자와 단위

- 금액은 `5억 원`만 쓰지 말고 필요 시 원 단위 raw 값 제공
- 비율은 분자·분모와 기간 명시
- 중앙값/평균/백분위 구분
- VAT 포함 여부 표시
- quantity와 unit 표시
- 환율 사용 시 기준일·source 표시
- 반올림 규칙 표시
- 표본 수 `n` 표시
- “최대”, “최저”는 coverage 범위 내라는 조건 표시

## 10. 제목 규칙

제목은 관측 사실과 질문 범위를 담는다.

허용:

- `동일 조건 공공계약 중앙값의 4.8배로 나타난 장비 구매`
- `3개월 동안 같은 업체와 연속 체결된 유사 용역 6건`
- `유지보수 포함 사실이 확인돼 가격 차이가 설명된 사례`

금지:

- `[단독] 세금 10억 증발`
- `역대급 비리 포착`
- `○○업체 게이트`
- `공무원들이 또 해먹었다`

공식 감사나 판결을 다루더라도 문서에서 확인된 범위를 넘어 확장하지 않는다.

## 11. 버튼과 경고 문구

- `게시` 대신 `승인된 revision 공개`
- `삭제` 대신 `철회 검토 시작` 또는 `비공개 법적 조치`
- `AI 실행` 대신 `보조 조사 실행 — 상태 자동 변경 없음`
- `확정` 대신 목적을 구체화: `기관 식별 확정`, `증거 검증 완료`
- 위험 action에는 결과를 명시: `새 revision을 공개하며 이전 revision은 이력에 남습니다.`

## 12. 빈 상태

나쁜 예: `아직 비리가 없습니다.`

좋은 예:

> 현재 선택한 조건에서 공개된 사례가 없습니다. 이는 문제 없음이나 청렴성을 의미하지 않으며, 수집 범위와 검토 상태에 따라 결과가 달라질 수 있습니다.

## 13. 오류와 장애

- `서버 오류`만 표시하지 말고 재시도 가능 여부와 data freshness 영향 설명
- source 장애 때 “새 자료 갱신이 지연 중”이라고 표현
- 기존 publication의 사실성이 자동 무효화된 것처럼 말하지 않음
- 내부 식별자, stack trace, source credential 노출 금지

## 14. AI 표시

AI가 작성한 초안, 추출 또는 분류는 내부에서 명확히 표시한다. 공개 문서의 책임 주체는 승인한 편집 체계다. 공개 페이지에 모델 이름을 홍보성으로 강조하지 않는다. methodology에는 모델 보조 사용 범위, 검증 방식, 버전 기록 원칙을 공개한다.

## 15. 정치·선거 관련 문구

정당, 선출직, 선거 기간이라고 기준을 바꾸지 않는다. 하지만 오해와 파급 위험이 커질 수 있으므로 source, 날짜, 직위, 당시 재직 여부, 공식 행위와 개인 행위를 분리한다. 자동 알림이나 추천 알고리즘이 특정 진영을 확대하지 않도록 coverage 통계를 내부 감시한다.

## 16. 법률 검토 trigger 단어

다음 표현이 draft에 포함되면 자동 lint와 법률 검토가 필요하다.

- 뇌물, 횡령, 배임, 사기, 담합, 유착, 리베이트
- 범죄, 불법, 위법, 유죄, 피의자, 공범
- 세금을 해먹다, 뒤를 봐주다, 특혜를 주다
- 개인의 정신·건강·성생활·가족 등 민감 정보

공식 문서의 정확한 명칭이나 인용으로 필요한 경우에도 attribution과 확인 범위를 붙인다.

## 17. 정정 품질

정정 notice는 다음을 답해야 한다.

1. 무엇이 틀렸는가
2. 왜 틀렸는가
3. 무엇으로 확인했는가
4. 제목·요약·결론·수치 중 무엇이 바뀌었는가
5. 당사자에게 어떤 영향이 있었는가
6. 같은 오류를 막기 위해 무엇을 바꿨는가

`일부 내용이 수정되었습니다`만으로 끝내지 않는다.

## 18. 검수 checklist

공개 문구마다 확인:

- [ ] 사실과 해석을 구분했는가
- [ ] claim마다 evidence가 있는가
- [ ] 날짜·기간·단위·분모가 있는가
- [ ] 비교 가능 조건을 설명했는가
- [ ] 불확실성과 반대 근거가 있는가
- [ ] 소명 상태가 정확한가
- [ ] 위법·부패를 자체 확정하지 않는가
- [ ] 제목이 본문보다 강하지 않은가
- [ ] 개인정보가 필요 최소 범위인가
- [ ] 정정·source freshness가 표시되는가
